# Fridge-to-Table — Product spec (demo, Oct 2026)

## 1. Background

- Part of an internal program, "50 Multimodal Agent Apps". Each idea gets a thin, working demo. A demo passes only if **a real person ran it on their own input and said they would use it again**. Demos that pass move on to a "deepening" phase: memory, continuity, a real user. The code is later released as open source.
- Company strategy: take app ideas proven in the West and bring them, with some added value, to markets where they do not exist yet. The full project will later add Chinese support and Huawei hardware. **None of that is in this demo.**
- Western precedents: FridgeSmart (inventory from photos, receipts and barcodes, meal plans, shopping lists), Samsung Family Hub (camera inside the fridge), Skylight Calendar (photo of the fridge → recipes and shopping list).
- Longer term, "what is where in this kitchen, right now" feeds a robotics interface layer (ATARI). That is context only, not demo scope.

## 2. The product in one sentence

A kitchen agent that knows what is in your home: photograph the fridge and pantry, then chat with it to get meals you can cook right now, or what you are missing for the dish you want. It remembers what your family likes and checks its own suggestions.

**Target user:** parents and working adults who cook at home regularly. The problem: "what do I cook tonight?" every day, forgotten food going bad, discovering a missing ingredient halfway through cooking.

## 3. Decisions (these override any older planning document)

| Topic | Decision |
|---|---|
| Language, cuisine | English only. General cuisine. |
| Team | One developer. |
| Usage modes | Mode A (what can I cook) and Mode B (I want to make X). Mode C (multi-day plan) is **out**. |
| Agent | A real agent: an LLM in a tool loop decides which tools to call. Deterministic code verifies. |
| Framework | Pydantic AI. No openJiuwen, no Ascend in the demo. |
| Models | Chinese models only, via API. Start with DeepSeek for all roles (agent: V4-Pro; recipes: V4-Flash; vision: V4-Flash-Vision-Exp, the only license available now). Switch vision to Qwen3.8 Max once that license is approved. Both swappable by env var (see §9). |
| Recipes | Generated by the model, checked by code. No hand-written recipe database. |
| Inventory correction | Editable side panel with uncertain items highlighted. The agent also asks about up to 3 uncertain items in chat. No separate clarification wizard. |
| Staples | Default editable list (salt, oil, ...) assumed present unless the user removes them. |
| Expiry | No expiry tracking. The user marks items "use soon". |
| Quantities | Coarse levels (plenty / some / low) always; an optional exact amount (g, kg, ml, l, pcs, pack) only when the user enters it (T6.3). Recognition never guesses amounts; the checks stay presence-based. |
| Coverage | The inventory is built from three places: fridge, freezer, pantry. The user tags each photo with its place. The agent tracks which places were scanned and asks for the missing ones. Until the pantry is scanned, pantry-type ingredients are never reported as definitely missing. |
| Persistence | Inventory and preferences persist across sessions. Chat history per session. |
| UI | Mobile web app: chat + inventory side panel (a drawer on a phone). |

## 4. Core flows

**Flow 1: build the inventory**
1. The user attaches 1–4 photos in the chat. Each photo gets a place tag (Fridge / Freezer / Pantry), chosen with one tap on its thumbnail; the default follows the order fridge → freezer → pantry. A pantry is usually several shelves or cabinets: several photos with the same tag are fine. They may write a message along with them, or nothing.
2. The agent calls `recognize_inventory`. The tag is passed to the model as the location, so it does not have to guess. Items appear in the side panel, uncertain ones highlighted at the top. The place is recorded as scanned, with a timestamp.
3. The agent sends a short summary ("Found 23 items. Two I'm not sure about: is the white container leftover rice? Is that yogurt or sour cream?").
4. If a place has not been scanned yet, the summary ends by asking for it once ("Want to add a photo of your pantry too? Then I'll know about your rice, pasta and cans."). The freezer is optional: ask for it once, and do not ask again if the user declines.
5. The user answers in chat, or edits the panel directly (delete, rename, change quantity, toggle "use soon").

**Flow 2: Mode A, what can I cook**
1. The user writes something like "What can I cook tonight?" or "something quick, 30 min, kids are eating".
2. The agent may first update the inventory if the message says so ("we're out of eggs").
3. The agent calls `suggest_meals` with the constraints, then `validate_suggestion` on each candidate. It replaces candidates that fail.
4. The reply shows up to 3 meal cards: name, time, which inventory items it uses (with "use soon" items marked). Tapping a card opens the full recipe.

**Flow 3: Mode B, I want to make X**
1. "I want to make lasagna."
2. The agent calls `get_recipe("lasagna")`, then `compute_missing`.
3. For each missing essential ingredient, the agent checks whether something in the inventory is a reasonable substitute (e.g. cottage cheese for ricotta) and proposes it.
4. The reply shows the recipe card, the substitutions it proposes, and a shopping list in two parts: **To buy** (definitely missing) and **Check your pantry first** (pantry-type ingredients — grains, pasta, canned goods, baking items, sauces and condiments, spices — that are not in the inventory while the pantry has not been scanned). Once the pantry is scanned, everything missing goes to "To buy".

**Flow 4: preferences (memory)**
- When the user states a lasting like or dislike ("the kids hated the eggplant", "we don't eat pork"), the agent calls `save_preference`.
- Stored preferences are injected into the agent's instructions on every run, and `validate_suggestion` rejects meals with an avoided ingredient.
- They persist across sessions. In a new session, suggestions respect them without being reminded.

**Flow 5: proactive opening**
- When the app opens and the inventory is not empty, the agent greets with a suggestion that targets "use soon" items ("Your spinach needs using. Want a spinach dish tonight?"). If no "use soon" items exist, it gives a short generic greeting with one quick idea.

**Stretch (only if the Oct 20 decision point passes):**
- "We cooked it": after the user confirms they cooked a suggested meal, the agent lowers the used ingredients (`plenty → some → low → removed`) via `update_inventory`.
- Share shopping list: a button that copies the list as plain text.

## 5. Agent behaviour

Instructions the agent must follow (encode them in the agent's instructions):

- Never claim an item is in the inventory without having read it via a tool in this run (`get_inventory`) or in the injected inventory summary.
- Before presenting any meal, it must pass `validate_suggestion`. If it fails, fix it: swap the meal, use a substitute from the inventory, or present it as a Mode B result with a shopping list.
- Prefer meals that use "use soon" items.
- Respect stored preferences. When the user states a lasting preference, save it.
- When the inventory has uncertain items, ask about at most 3, in one message.
- Know which places were scanned (fridge, freezer, pantry; it is in the injected inventory summary). After a scan, ask once for a place not yet scanned. Never say a pantry-type ingredient is missing while the pantry has not been scanned: put it under "check your pantry first". When suggesting meals in Mode A without a pantry scan, rely only on what was scanned plus staples, and mention once that a pantry photo would give more options.
- Keep replies short. Meals go in structured cards, not prose.
- Never order, buy or delete anything on the user's behalf without an explicit request.
- At most ~8 tool calls per turn. If stuck, answer with what it has.

## 6. Tools (contracts)

All tools live in `app/tools/` as plain functions with Pydantic I/O. The agent wraps them.

| Tool | Kind | Input → Output |
|---|---|---|
| `recognize_inventory(image_paths)` | LLM (vision) | images → `list[InventoryItem]` (draft, with `confidence`, `uncertain`) |
| `get_inventory()` | code | → `list[InventoryItem]` (confirmed + staples) |
| `update_inventory(changes)` | code | `list[InventoryChange]` (add / remove / set_qty / set_use_soon / rename / confirm / add_staple / set_amount) → updated inventory |
| `suggest_meals(constraints, n, exclude)` | LLM (text) + code | free-text constraints, how many, dishes to exclude → `SuggestResult`: candidates (id, name, ingredients, time; **no steps**) already run through `validate_suggestion`, split into `passed` and `failed` (with the reason) |
| `get_recipe(dish)` | LLM (text) | dish name → `Recipe` (no steps); the agent sees it as a `MealCandidate` |
| `get_steps(recipe_id)` | LLM (text) | recipe id → the same `Recipe` with `steps` filled; generated on first request, then stored. Called by the API when the user opens a card, never by the agent |
| `compute_missing(recipe_id)` | **code** | id of a recipe from this run → `MissingReport` (essential ingredients missing, after normalization and staples) |
| `validate_suggestion(recipe_id)` | **code** | id of a recipe from this run → `ValidationResult` (ok, missing essentials, violated preferences). Still a separate tool: for Mode B dishes and for re-checks after an inventory change in the same turn |
| `save_preference(text, avoid)` | code | free text + list of canonical ingredients to avoid → `Preference` |
| `get_preferences()` | code | → `list[Preference]` |

Notes:
- `suggest_meals` and `get_recipe` receive the current inventory and preferences inside their prompt, and must return structured `Recipe` objects. Their output is never trusted: `validate_suggestion` / `compute_missing` decide.
- **Recipes by reference (the recipe cache).** Every `Recipe` has a short random `id`. Each recipe a tool returns is kept in a per-run cache (`Deps.recipes`) and saved in the store by id. The agent refers to recipes only by id: `compute_missing` / `validate_suggestion` take an id, and the final reply carries `meal_ids`, never recipe content. After the run, code fills `AgentReply.meals` with the full `Recipe` objects from the cache. This keeps the model from re-typing recipes (it was 15-20 s of the turn) and removes copy errors.
- **Steps on demand.** Candidates and Mode B recipes are generated without cooking steps (steps were most of the generation time). The UI shows name, time and ingredients on the card; when the user opens a card the API calls `get_steps(recipe_id)` once and stores the steps with the recipe.
- Substitutions in Mode B are proposed by the agent itself (it has the inventory). The output validator checks that every proposed substitute is in the inventory.

## 7. Data model

```python
QtyLevel = Literal["plenty", "some", "low"]
Location = Literal["fridge", "freezer", "pantry"]

class InventoryItem(BaseModel):
    id: str
    name: str               # canonical, from normalize()
    display_name: str       # what the user sees, e.g. "Greek yogurt"
    category: str           # vegetable, fruit, meat, fish, dairy, egg, grain, pasta, canned, baking, sauce, condiment, spice, snack, drink, frozen, other
    qty_level: QtyLevel
    location: Location
    confidence: float       # 0..1, from recognition; 1.0 for manual
    uncertain: bool         # confidence below threshold, or flagged by the model
    use_soon: bool = False
    is_staple: bool = False
    source: Literal["photo", "chat", "manual", "staple"]
    updated_at: datetime
    amount: float | None = None   # optional exact amount, only from the user (panel or chat), stored as entered
    unit: Literal["pcs", "g", "kg", "ml", "l", "pack"] | None = None
    amount_text: str              # computed for display: "2 l", "1.5 kg", "" when no amount

class Ingredient(BaseModel):
    name: str               # canonical
    amount: str             # free text, "300 g", "2", "a handful"
    essential: bool
    category: str           # same categories as InventoryItem; used to decide what is pantry-type

PANTRY_CATEGORIES = {"grain", "pasta", "canned", "baking", "sauce", "condiment", "spice", "snack"}

class ScanState(BaseModel):
    scanned: dict[Location, datetime]   # place → last scan time; absent = never scanned
    freezer_declined: bool = False

class Recipe(BaseModel):
    id: str                 # short random id ("a3f9c1"); what the agent and the API refer to
    name: str
    ingredients: list[Ingredient]
    steps: list[str] = []   # empty until get_steps() fills them on demand
    time_minutes: int
    servings: int = 4
    uses_from_inventory: list[str] = []   # canonical names, filled by code, not by the model

class MealCandidate(BaseModel):          # what the agent sees of a recipe (no steps)
    id: str
    name: str
    time_minutes: int
    ingredients: list[str]  # "tomato: 2", "parsley: a handful (optional)"
    uses_from_inventory: list[str] = []

class FailedCandidate(BaseModel):
    id: str
    name: str
    reason: str             # from validate_suggestion

class SuggestResult(BaseModel):          # suggest_meals output, already checked by code
    passed: list[MealCandidate]
    failed: list[FailedCandidate]

class Preference(BaseModel):
    id: str
    text: str               # "kids dislike eggplant"
    avoid: list[str]        # canonical ingredients
    created_at: datetime

class MissingReport(BaseModel):
    missing_essential: list[str]   # definitely missing ("To buy")
    check_first: list[str]         # pantry-type, pantry not scanned ("Check your pantry first")
    missing_optional: list[str]

class ValidationResult(BaseModel):
    ok: bool
    missing_essential: list[str]
    violated_preferences: list[str]
    check_first: list[str] = []
    reason: str = ""        # one line for the agent

class StepTiming(BaseModel):             # one timed step of a turn (model call or tool call)
    kind: Literal["model", "tool"]
    name: str
    seconds: float
    detail: str = ""
    input_tokens: int | None = None
    output_tokens: int | None = None

class Substitution(BaseModel):
    missing: str
    use_instead: str        # must be in the inventory (checked)

class ToolTraceItem(BaseModel):
    tool: str
    args_summary: str
    result_summary: str

class AgentReply(BaseModel):
    message: str                         # short text
    meal_ids: list[str] = []             # ids of recipes returned by tools in this run: Mode A cards (max 3) or the Mode B recipe
    meals: list[Recipe] = []             # filled by code from the run's recipe cache (hidden from the model's schema)
    substitutions: list[Substitution] = []
    shopping_list: list[str] = []        # "To buy"
    check_first: list[str] = []          # "Check your pantry first"
    questions: list[str] = []            # clarifying questions about uncertain items (max 3)
    # trace is attached by the server from the run's messages, not produced by the model
```

**Exact amounts (T6.3, `app/amounts.py`).** `qty_level` is always set and is what the checks use. The exact amount is optional and comes only from the user: the panel's Amount line, the add field ("milk 2 l", "6 eggs"), or chat ("we have 6 eggs" → `set_amount`). Recognition never guesses one. `InventoryChange` op `set_amount` (name, amount, unit; amount null or 0 clears it; unit null = the category default) never changes `qty_level`; rename, confirm, set_qty and later photos keep the amount. Helpers, all deterministic:
- `parse_amount(text)` → `(amount, unit)` or None: "300 g", "1.5 kg", "500ml", "2 l", "2" (pcs), "1/2 l", "about 300 g" parse; "a handful", "2 tbsp", "1 lb" → None.
- `to_base(amount, unit)` → `(value, base_unit)`: kg → g ×1000, l → ml ×1000; g, ml, pcs, pack stay.
- `format_amount(amount, unit)` for display: 1500 g → "1.5 kg", 0.5 l → "500 ml".
- `default_unit(category, name)`: egg, fruit, vegetable → pcs; meat, fish, dairy (cheese), grain, pasta, baking → g; drink and milk → l; sauce → ml; otherwise pcs.

The checks stay presence-based: amounts are never compared with recipe amounts. T6.1 "I made it" and T6.4 "Bought it" will use `parse_amount` / `to_base` to subtract or add when the units are compatible, and otherwise move `qty_level` by one step.

**Matching rule (used by `compute_missing` and `validate_suggestion`):** an ingredient counts as available if its canonical name equals an inventory item's canonical name, or both map to the same entry in `data/synonyms.json`, or it is in the staples list (and the user has not removed that staple). Items with `qty_level == "low"` still count as available. Optional ingredients never fail validation.

**Unscanned pantry rule:** if the pantry has never been scanned, a missing essential ingredient whose `category` is in `PANTRY_CATEGORIES` goes to `check_first`, not `missing_essential`. In Mode A, `validate_suggestion` still fails such a meal (we only suggest from what we know is there), and the failure reason says "pantry not scanned" so the agent can mention it.

## 8. UI

One page, mobile first.
- **Chat** (main area): message bubbles; an attach-photo button (camera or gallery, up to 4); text input. Before sending, each photo thumbnail shows a place tag (Fridge / Freezer / Pantry) that cycles on tap.
- **Meal cards** inside agent messages: name, time, the inventory items it uses (chips; "use soon" chips highlighted). Tap → full recipe in a bottom sheet.
- **Shopping list** block inside agent messages when present: substitutions on top, then "To buy", then "Check your pantry first" (muted style).
- **Trace line** under each agent message, collapsed by default: "3 tools · updated inventory → 5 candidates → 1 failed (no cream) → replaced". Expanded: one line per tool call.
- **Inventory panel**: a drawer opened from a header button, with a count badge. Grouped by location; each location header shows "scanned 2 days ago" or "not scanned yet" with a camera button that opens the photo picker pre-tagged with that place. Uncertain items at the top with a warning style. Each item: name (with its exact amount when set: "Milk · 2 l"), quantity level dot, and on tap its actions: quantity level, "use soon" toggle, rename, delete, and an **Amount** line (a number input that accepts 1.5, unit chips pcs / g / kg / ml / l / pack with the category's default preselected, Save, Clear; saved with `PATCH /inventory` `set_amount`). "Add item" input, which also accepts an amount ("milk 2 l", "6 eggs"). A "Staples" section that can be collapsed.
- Loading state while the agent runs. If possible, stream the message text.

## 9. Model choice

**Constraint: only Chinese models may be used.** Right now the only license is DeepSeek (unlimited). Other providers need a license request.

**Agent: DeepSeek V4-Pro** (`deepseek-v4-pro`). The license is unlimited, so cost is not a factor: start with the stronger model for tool selection and self-correction. If turns are too slow (T5.2), try `deepseek-v4-flash`, which DeepSeek reports is on par with Pro on simple agent tasks, and rerun the scenarios.

**Recipes: DeepSeek V4-Flash** (`deepseek-v4-flash`) for `suggest_meals` and `get_recipe`. A single structured generation call, where speed matters more, and every result is checked by code anyway.

Both are open-weight and already supported by vLLM on Ascend, which helps the full project later.

**Vision, to start: DeepSeek V4-Flash-Vision-Exp** (`deepseek-v4-flash-vision-exp`). Known weaknesses:
- Experimental (released Aug 21, 2026), no stability guarantee.
- Each image is capped at about 384 tokens, which is little for a crowded fridge or for reading pantry labels.
- Weak on the public benchmark (table below).

Mitigation: **image tiling** (T1.4). Each photo is split into 2–4 overlapping crops, each sent as its own call, so every item gets more of the token budget.

**Vision, target: Qwen3.8 Max**, once the license is approved. It is the best Chinese vision model on the benchmark, ranked 7 of 61 overall and first on counting. Its license is listed as Apache-2.0 with weights announced for public release, so it can later run on Ascend.

## 10. Acceptance criteria (demo is ready when all hold)

- [ ] ≥ 70% of visible items correctly identified before correction, on the eval set.
- [ ] ≤ 2 hallucinated items per photo on average.
- [ ] Every meal shown to the user passed `validate_suggestion` (enforced by the output validator).
- [ ] At least once in the demo, the trace shows the agent fixing a failed suggestion.
- [ ] "We're out of eggs, something in 30 minutes" updates the inventory, then suggests meals that need no eggs and take ≤ 30 min.
- [ ] A preference stated in one session changes suggestions in a new session.
- [ ] Mode B returns only what is truly missing, and proposes a substitute when one is in the inventory.
- [ ] With only the fridge scanned, the agent asks once for the pantry, and Mode B puts pantry-type items under "Check your pantry first", not "To buy".
- [ ] Recognition on the pantry eval sets meets the same targets as on fridge sets (labels on jars and packages are read).
- [ ] Photo upload → inventory in panel: < 30 s. Meal request → reply: < 25 s.
- [ ] Inventory and preferences survive a server restart.
- [ ] The real user runs the full flow and says they would use it again.

(The numeric targets are first guesses. Calibrate them on Oct 20.)

## 11. Out of scope

Mode C (multi-day plans), structured family profiles, Chinese language and dishes, expiry estimation, receipts, delivery-app export or ordering, voice, video, live cooking guidance, multi-agent setups, auth or multiple households, Ascend, openJiuwen, native mobile apps.

## 12. Demo script (about 5 minutes, Oct 23)

1. Open the app on a phone. The proactive greeting suggests something with the "use soon" spinach (set up beforehand).
2. Photograph a real fridge (2 photos) and pantry (1). The panel fills with about 25 items. The agent asks about 2 uncertain ones. Answer in chat.
3. "What can I cook tonight? Something under 30 minutes, the kids are eating." Three cards. Open the trace: one candidate failed validation and was replaced.
4. "The kids hated the eggplant last time." The agent saves the preference.
5. "I want to make lasagna." Recipe, one substitution from the inventory, a shopping list of 3 items.
6. Reload the app (new session) and ask for dinner ideas. No eggplant. Point out that it remembered.
